# Database

MongoDB, database name `sfplatform` (deliberately separate from CyberLab's own `sentinelforge` db — same physical Mongo server is fine to reuse, but the two apps never share a database). Mongoose models live in `sentinelforge/backend/src/db/models.ts`, one model per collection, each with an explicit TypeScript interface (Mongoose's automatic type inference proved unreliable for several fields during development — see `docs/IMPLEMENTATION-STATUS.md` — so every model is typed explicitly).

## Collections

| Collection | Purpose | Key fields |
|---|---|---|
| `organizations` | tenant for SentinelForge itself | name |
| `users` | SentinelForge accounts | email (unique), role (admin/analyst/viewer), passwordHash |
| `applications` | a registered target (CyberLab) | baseUrl, adapter, status, discovered |
| `assets` | discovered services under an application | kind, name |
| `endpoints` | discovered routes | method, path, authRequired |
| `scan_runs` | one scan execution | status, checksTotal, findingsOpen |
| `scan_results` | one check's raw outcome | vulnKey, outcome, request, response (evidence) |
| `vulnerabilities` | normalized findings | vulnKey (unique per application), severity, status, evidence, aiAnalysis |
| `security_events` | ingested CyberLab events | source+sourceId (unique, dedupe key), eventType, sourceIp, userId, metadata |
| `detections` | a rule match | rule, subject, evidence, eventIds |
| `incidents` | auto-created from a detection | rule, subject, severity, status, investigation |
| `correlations` | finding ↔ incident link | findingId, incidentId, evidence, reason |
| `attack_paths` | one per incident | nodes[], edges[] (React Flow shape) |
| `remediation_tasks` | applied-fix record | findingId, plan, appliedAt |
| `verification_runs` | one verify click | findingId, passed, before, after |
| `response_actions` | incident response | action, status (PENDING_APPROVAL/EXECUTED/REJECTED), highImpact |
| `audit_logs` | every sensitive action | actor, action, targetType/targetId, details |
| `threat_indicators` | local CWE/OWASP/CVE/EPSS/CISA-KEV reference data, synced after every scan | kind ("cwe"), value, details |
| `agent_runs` | full audit trail of every AI agent invocation | agent name, subjectType/subjectId, status, `toolCalls[]` (every tool call's args + success/failure), output |
| `simulation_runs` | reserved for simulation history | not populated yet — results are returned inline from `POST /api/applications/:id/simulate/:scenarioId` rather than persisted separately |

## Key relationships

```
Application -> Asset -> Endpoint -> Vulnerability
User (CyberLab-side, by id string) -> SecurityEvent -> Detection -> Incident
Vulnerability <-> Correlation <-> Incident -> AttackPath
Vulnerability -> RemediationTask -> VerificationRun
Incident -> ResponseAction
```

There are no foreign-key constraints (Mongo doesn't have them) — relations are enforced in application code (`modules/*/service.ts`), and every id reference is a plain string, not an ObjectId, so ids are human-readable in logs and the API (`vuln_...`, `inc_...`, `ev_...`, generated by `lib/util.ts: newId()`).

## Indexes

- `security_events`: `(source, sourceId)` unique (dedupe), `timestamp` desc, `eventType`, `userId`, `tenantId`, `sourceIp`, `endpoint` — matches the master spec's required index list.
- `vulnerabilities`: `(applicationId, vulnKey)` unique, `severity`, `status`.
- `incidents`: `severity`, `status`, `detectedAt` desc.
- `correlations`: `(findingId, incidentId)` unique.
- `endpoints`, `assets`: unique per application to make discovery idempotent (`upsert`-style).

## Migrations / seeding

No formal migration runner — Mongoose's schema is the source of truth and collections are created on first write. `npm run seed` creates the organization + admin/analyst accounts from env-provided passwords (refuses to run without them, see `config.ts: assertSeedCredentialsPresent`). `npm run demo:reset` clears every SentinelForge-owned collection and resets CyberLab's lab-fix toggles, without touching CyberLab's own database or SentinelForge's `users`/`organizations` (so you don't need to re-seed credentials between demo runs).
